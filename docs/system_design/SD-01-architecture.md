# SD-01: независимые образовательные направления

База: C++ Recall, `706e078`. Один процесс, один Telegram-вход, два направления:
`cpp` и `system_design`. Это разделение предметных моделей, а не микросервисы.

## Общие компоненты

Проверка Telegram initData, числовая пользовательская идентичность, профиль,
HTTP-сервер, ограниченный пул PostgreSQL и дизайн Mini App. У пула есть узкий
`WithConnection`: эксклюзивное соединение действует только внутри callback.
Новая модель не получает доступ к реализации C++ репозитория.

## Независимые компоненты

C++ сохраняет QuestionBank, Question/Task, темы, навыки, маршруты, сессии,
XP, освоение и интервальное повторение. В его каталоги не добавляются SD-задания.

`system_design::Service`, `Repository` и отдельный типизированный `catalog`
обслуживают вводный модуль и архитектурные кейсы. Модель этапа различает требования,
расчёты, контракт, данные, архитектуру и компромиссы. Общего движка заданий нет.

## Доступ и маршруты

Существующий `MINI_APP_FEEDBACK_ADMIN_ID` уже описывает неизменяемый Telegram ID
владельца. Новая настройка не требуется. Положительное точное совпадение с ID из
проверенного initData — единственный способ доступа. Username и поля тела запроса
не используются. Отсутствующая настройка закрывает доступ; неправильная не даёт
запустить конфигурацию. Секреты для разработки не читаются.

В authenticated bootstrap обычному пользователю возвращается только `cpp`,
владельцу — оба направления. `/api/v1/system-design/*` требует владельца до
разбора тела; сервис повторяет проверку на каждом действии. Неавторизованный
запрос получает 401, чужой ID — 403. Отдельной публичной SD-страницы нет.
Публичный JS содержит только UI, не учебный каталог, подсказки или готовые разборы.

Действия: bootstrap, module, complete-module, start, current, session, save,
hint, advance, self-review. Сессии и версии SD передаются отдельно от C++ session_id.

## Хранение и восстановление

Добавочная миграция `019_system_design.sql` создаёт только SD-таблицы:

- `system_design_module_progress`: ознакомление с редакцией модуля;
- `system_design_sessions`: кейс/редакция, этап, ответы, черновики, открытые подсказки;
- `system_design_commands`: ключи идемпотентности и принятые версии изменений;
- `system_design_results`: сохранённый итоговый разбор и явная самооценка.

История — отдельные начатые/завершённые SD-сессии; статистика считается по всем
их строкам, независимо от лимита выдачи истории. Связь только с общим `users`.
Нет записей в C++ attempts/question_progress/skill_evidence/xp и нет domain_id
в старых таблицах. Доступ к строкам всегда ограничен authenticated user_id.

Команды сохраняются транзакционно, с блокировкой SD-сессии и проверкой версии.
Повтор того же request_id с теми же данными не применяет действие снова;
другие данные под тем же ключом отвергаются. Старая версия не перетирает черновик.
Соединение не переподключается посреди транзакции. Начало сериализовано по SD-user,
одновременно начатый тот же кейс возвращает уже существующее незавершённое занятие.

## Учебный процесс и честная оценка

Сначала вводный модуль, затем 12 этапов сокращателя ссылок. Каждый переход требует
собственного непустого ответа; это проверка наличия текста, не его корректности.
Подсказки открываются последовательно и сохраняются на сервере. До завершения
нет полного решения/разбора в ответе API. Итог сохраняет собственные ответы,
рубрику, альтернативы и первичные источники. Отметки «обосновано / сомневаюсь /
упущено» — самооценка владельца, не алгоритмический вердикт или mastery.

Автоматический смысловой рецензент, рисование диаграмм, оценка по единственному
эталону, XP и система навыков SD в пилот не входят. Для дальнейшей системы навыков
нужны собственные компетенции и доказательства применения/переноса знаний;
чтение модуля и самооценка не должны автоматически подтверждать навык.

## Клиент и переключение

Сохраняются прежние компоненты и Telegram-темы. Выбор направления запоминается
с authenticated user_id и сверяется с разрешённым сервером списком. C++ DOM и
активная сессия не пересоздаются при переключении; незапрошенные отправкой
ответы сохраняются отдельно по user/session/question/revision. SD имеет собственное
состояние и серверные черновики с локальным восстановлением при сетевом сбое.
SD-экран не посылает C++ activity и не присваивает ему время открытой C++ карточки.
При конфликте версий навигация не заменяет несохранённый текст. Локальная копия,
изменённая другим окном, не удаляется даже из окна без собственных изменений.

Визуальный контракт остаётся в `docs/miniapp/style.css`: прежние Telegram-темы,
поверхности, системный шрифт и компоненты, без новой визуальной системы. Поля —
16 px, основные действия — не менее 48 px. В светлой теме ошибки имеют отдельный
контрастный цвет; подпись SD говорит о сохранении решений и самопроверке, не об
автоматическом признании ответа верным.

## Добавление материала

Добавлять новые `Module`/`Case` в отдельный каталог, с неизменяемыми ID и редакцией,
конкретным заданием, независимыми подсказками, рубрикой, альтернативами и первичными
источниками. При изменении смысла повышать редакцию; старую активную редакцию
нужно продолжать обслуживать либо явно мигрировать, не менять выданное задание молча.
Не переносить SD-материал в C++ QuestionBank ради повторного использования UI.

## Проверка

Нужны тесты реальных signed HTTP-запросов, запрета доступа, повторов/конфликтов,
перезапуска, независимости C++ строк и browser-переключения с черновиками.
Ширины 390/768/1440, светлая/тёмная тема; реальные Telegram-клиенты — отдельная приёмка.
Фактические результаты и ограничения фиксируются в локальном отчёте SD-01,
а не выводятся из наличия этого документа. Публикация и выпуск — отдельные операции,
не следующие автоматически из реализации направления.
